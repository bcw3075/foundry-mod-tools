# Foundry traps and code notes (for every module Claude builds for Rhea)

Moved here word for word from the foundry-module-dev skill on 2026-11-10 (efficiency review, item 2), so a chat
pays for these lines only when it writes code. The section numbers are the skill's own, kept so older references
("foundry-module-dev section 8") still land. **This file is their one home now:** add a new general trap here,
in the section it belongs to, in the same step it is found.

How to use it (the gate wants `- traps-read done: <what was read>` under the record's Setup when code changed):
- `python3 ../foundry-mod-tools/guide.py traps` lists the sections with their sizes.
- `python3 ../foundry-mod-tools/guide.py traps <word> [<word> ...]` prints every bullet that names any of the words
  (for example `traps combat turn initiative` before touching the turn loop, `traps region tile` before map work).
- `python3 ../foundry-mod-tools/guide.py traps --section 4` prints one section whole. Read section 4 in full before
  the first code of a new module, and search section 8 by the things the change touches before each change.
- Section 5 is the release and install steps: the gate prints `guide traps --section 5` when it has built the zip.

## 4. Module structure
- `module.json`: `id`, `title`, `version`, `compatibility` {minimum 13 or 14, verified "14"}, `esmodules`, `styles`, `languages` if any, `relationships` (`systems: [{id:"pf2e", type:"system", compatibility:{minimum:"8.0"}}]`; requires: libWrapper/socketlib only if used), `manifest` = raw GitHub URL of `module.json` on `main`, `download` = raw GitHub URL of a zip **committed in the repo** (`dist/<id>.zip`, files at the zip root).
- Code: ES modules under `scripts/`; keep **pure logic** (generation, maths, parsing) in files with no Foundry globals so they run in a plain browser or plain Node for local tests; keep Foundry glue (hooks, documents, UI) apart from them.
- API: `game.modules.get(ID).api = {...}` in a `ready` hook; GM-only calls check `game.user.isGM`. A good API makes bridge `run_script` testing easy.
- Settings: register in `init`. World data the module owns → world settings (`config: false`, type Object). Per-scene data → scene flags `flags[ID]`. Mark every document the module creates with a flag (e.g. `flags[ID].enc`) so a rebuild deletes only its own documents and never the GM's. Flags must use the module id as scope: a made-up scope throws.
- When data is stored or exported, keep every field the consumers need (e.g. a survey slice's height fields): a check that compares only part of the data (a terrain fingerprint) won't catch what was dropped.
- Hooks that change documents run on **the active GM only** (`game.users.activeGM?.id === game.user.id`); tag the module's own updates with an option (e.g. `{[ID]: {sync: true}}`) and ignore them in hooks to avoid echo loops.
- **Hook handlers return nothing: always a block body** (`c => { f(c); }`, never `c => f(c)`). Core fires `canvasReady` and others with `Hooks.call`, where a handler returning `false` stops every later handler from every module, with no error anywhere. `Set#delete` returned false and silently cut off 20 modules' handlers for a day (2026-11-05). `preCreate*` handlers returning false also cancel the document. Add a check for it to the module's local tests; to test live, `Hooks.call("canvasReady", canvas)` must return true.
- **An update merges objects into what's stored:** to replace a whole object (a plan, a record) use `foundry.data.operators.ForcedReplacement.create(value)` as the value, or old keys stay. Arrays are replaced anyway.
- When more than one browser writes the same flag, send only the change (`{[`flags.${ID}.path`]: change}`, which core merges), never a whole merged copy, which can put back what the other browser just wrote.
- UI: put a module's tools in **its own left-bar control group** (`getSceneControlButtons`; tools with `onChange`, `button: true` for one-shot actions; a mode tool shows as `ui.controls.tool.name`). Canvas clicks: `canvas.stage.on("pointerdown", ev => ev.getLocalPosition(canvas.stage))`.
- Dialogs: `foundry.applications.api.DialogV2.input({window, classes, position, content, ok})` returns form data. **DialogV2 strips `<style>`** from content: inject a `<style id>` into `document.head`. The browser caches module CSS across releases, so new styling can't rely on `styles/*.css` alone. Cap dialog height to the window and let it scroll (a tall dialog hid its submit button off-screen). In your own ApplicationV2 window, give it a fixed footer instead of a sticky bar, and minimise it while a preview needs the map.
- Files: upload generated images with `FilePicker.implementation.upload` into a module folder (`assets/<something>/`), versioned file names or `?v=` to dodge caches. WebGL textures max 16,384 px a side.
- **`docs/DEVELOPING.md` in every repo**: the general part (layout, data stored, hooks rule, testing, releasing) and a feature index generated by `guide --index` (never hand-edited); per-feature design reasons, decisions, checks and traps live in `docs/features/<name>.md`. It travels with the code, so the knowledge survives even without the skills. Technical only — the repo is public; the privacy scan checks it.
- Determinism: key anything generated to fixed world positions/lattices and a seed, so rebuilds are identical and extending never moves things.
- One module reading another's data: give it a pure read with a `schema` number the reader refuses if it doesn't know it, and a hook after changes; let the reader fall back in plain words if the other module is missing.
- **Work on a page nobody watches** (the Claude Bridge's): a dialog there waits for ever. Give each step a time limit, stop as soon as a window that looks like a prompt opens, close what opened, and record the step so nothing repeats. Check both `ui.windows` (v1 apps, such as PF2e's Modifier dialog) and `foundry.applications.instances`.
- **Before building a designed feature, have an independent reviewer read the design against the code** (2026-11-11): it is worth its cost. For a design whose lines were each to be written "when something happens", the review found that most of the planned lines had no event source in the code (the hooks heard only the module's own cards), which turned the build's first step into a live probe of what the system records instead of code built on a guess.

## 5. Release and install (verified flow)
1. Bring the feature docs and `docs/DEVELOPING.md` up to date with the change, and reread what `guide --diff` printed (the scripts can't see changed behaviour). Bump `version` in `module.json`.
2. Run `python3 ../foundry-mod-tools/gate.py` (section 0): it refuses until docs, checks, review and the scan are in order, then **builds the zip itself** from the tree and stamps it (the manifest downloads the committed zip; a stale zip installs old code, and a hand-built one is forbidden).
3. Commit and push `main` (work is on `main` directly); the `pre-push` hook re-checks the stamp on `main`. Repos not yet on the protocol (Survey Sheet, the bridge): run `python3 tools/doccheck.py`, rebuild the zip with `rm dist/<id>.zip && zip -qr dist/<id>.zip module.json styles scripts icons` (whatever folders exist), and adopt the protocol when next touched (section 10).
5. Poll until raw GitHub serves the new version in **both** `module.json` and the zip (`unzip -p` the downloaded zip's module.json).
6. Browser pane: `/join` → "Return to Setup" → confirm "Yes". The button sits in a collapsed section: click its "Return to Setup" label (find it with `find "setup"`), then click the "Yes" that appears. If it lands on `/auth`, ask Rhea to type the admin password (the unlock doesn't last: check `/join` for "authenticated as a server administrator" before every install; foundry-vtt-operator section 1).
7. On `/setup`, install by POST (the Install Module form sometimes reinstalled a cached version), **polling until the version matches**: one install still showed the old version after 12 s, and sending the next steps in the same batch hid that until the world had relaunched.
```js
await fetch('/setup',{method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({action:'installPackage',type:'module',id:'<id>',manifest:'<manifest url>'})});
let v; for (let i=0;i<14;i++){await new Promise(r=>setTimeout(r,2000)); v=(await (await fetch('/modules/<id>/module.json',{cache:'no-store'})).json()).version; if(v==='<new>')break} v
```
- **Installing the same version again** (a second test build): the version can't tell old from new, so compare a changed file's text (a phrase only the new code has). A script's `.length` counts characters, not the bytes `wc -c` gives, so a size check must allow for that (a wait loop on the byte count never matched, 2026-11-11).
- **A GM's own Return to Setup from inside the game is no way round the unlock** (14.370, 2026-11-11): it closes the world and then lands on the administrator password page all the same when that browser isn't unlocked, leaving no world running until the password is typed. Ask for the unlock first.
8. Reload `/setup` (navigate, then wait ~2 s before looking for the button), click `[data-package-id="pf2-test"] [data-action="worldLaunch"]` (from a `setTimeout`, so the script returns before the page navigates), wait ~10 s, at `/join` set `select[name=userId]` to AI (dispatch `change`) and click Join. Wait ~10 s. The bridge rejoins by itself within about 20 s; confirm with `foundry_status` and check `game.modules.get(id).version` through `run_script`. **A module that runs on the Bridge's page: refetch its files there too with `fetch(url,{cache:"reload"})` and reload that page, as for the pane.**
9. A brand-new module must be switched on for the world: set `core.moduleConfiguration` through the bridge before going back to setup (setting it before the install is fine), then relaunch.
10. After launch, and on every page each chat uses: Simple Calendar Reborn's client setting `open-on-load` **comes back on** (it was back on the Bridge's page after a relaunch in the 0.13.0 chat, and on every fresh hidden session) and its window (`fsc-if`, classes `simple-calendar`) covers the canvas. It's the page check `calendar-off`: run the repo's `tools/setup/calendar-off.js` through `run_script` on target `bridge`, each started session, and the pane's console; it sets the setting off and closes the window (verified 2026-11-09: a fresh AI session went from on to off and its window closed). The game may be paused.
- Installing restarts the world: in pf2 only with nobody else online and her OK.
- **The browser pane for setup work (2026-11-06):** its join page's Return to Setup needs the admin password unless the pane itself is unlocked ("You are authenticated as a server administrator" shows when it is); Rhea unlocking in her own browser doesn't count. Under 1024 px wide, Foundry warns and the confirm click didn't land: check `innerWidth` first.
- **With the browser pane hidden (`innerWidth` 0), do setup work by script on its page (2026-11-07):** click Return to Setup and its Yes with `element.click()`, POST the install, then click `worldLaunch` from a `setTimeout`. Screen clicks may not land there, and this needs no second window. Check `/join` says the pane is authenticated as a server administrator first.
- **A black screen on joining through the website means a big world download first:** check the chat log's size before anything else. 7 MB of test cards stalled the pane and Rhea's browser for over a minute (every file loaded, `game` stayed a plain object), while the Bridge and hidden sessions, which connect on the server PC, joined at once. Test cards are cleaned up after every round (foundry-test-process).
- **In a `--depth 1` clone the gate refuses with `git diff --name-only <base> failed: fatal: bad object`** (2026-11-11): the record's base commit isn't in the shallow clone. Run `git fetch --depth=200 origin main` first, then the gate passes.
- **The gate wants the close-out pass before the first push of a test build** (2026-11-11, Encounter Builder 0.26.0): when `guide start` says a close-out is due, three unverified items must be closed (verified live, dropped with a reason, or true duplicates merged into one) before the test build can be pushed at all, so the cheapest closures are planned while the code is being written, not after the install.
- **A record-only change after a release still goes through the gate and the hook** (2026-11-11, marking a card saved in a released record): run the full gate and switch the hook on (`git config core.hooksPath tools/githooks`) before the push to `main`. The zip comes out unchanged, so nothing needs installing again.

## 7. Local test harness pattern
- Commit the harness to the repo under `tools/test/` with real data git-ignored (`tools/test/data/`, `tools/test/out/`, `__pycache__/`); the survey sheet's harness is the model (server.js, page.html, render.js, find.js, contact.py, README). Pure logic with no canvas runs directly in Node (`node tools/test/unit.mjs`; the Encounter Builder's is the model), which is far quicker.
- Pure modules run in headless Chromium via Playwright (pre-installed: `require('playwright')`). ES modules need **http**, not file://: a tiny `http.createServer` serving the repo's `scripts/` and the data folder, so tests always use the working code.
- A test page imports the module code and exposes `window.render(data, opts)`; a node runner passes jobs as JSON and saves outputs as images. Real data comes from Foundry exports (bridge `run_script` or the module's export call), saved as project docs.
- Build contact sheets (PIL) to compare variants side by side: every case × every setting.
- **Check a copy of a PF2e function against PF2e itself (2026-11-07):** through `run_script`, fetch `/systems/pf2e/pf2e.mjs`, cut the function out by name (find `) {` after `function <name>(`: default parameters have braces of their own), and run it with `new Function("canvas", "CONST", "PIXI", src + "\nreturn <name>;")` and a stub `canvas` such as `{ grid: { type: CONST.GRID_TYPES.SQUARE, sizeX: 100 }, dimensions: { size: 100, distance: 5 } }`. Thousands of cases in a second against the installed system's real code, nothing in the world touched (140,800 distance cases for Encounter Builder 0.8.3). Then confirm on real placeables.
- Console scripts in the browser pane die at **45 s**: start long work without awaiting, store the result on `window`, poll.
- **Racing two pages in a live test** (2026-11-13, Encounter Builder 0.33.1): the chat's tool calls run one after another, even when sent together, so a script that waits for a moment blocks the next call until it returns. To make two pages act in the same instant, start the first page's work without waiting (an `async` function started and left running, the call returning at once), then the second's, both waiting for the same `game.time.serverTime` (the server's clock, the same on every page): two GM pages then saved within 3 ms of each other. A busy loop through the bridge's `run_script`, background or not, did not stop the runner's page from handling another page's request, so it is no way to hold the runner still.

## 8. Foundry v14 + PF2e traps (verified, 14.369 / 8.6.1 unless noted)
- `updateToken` fires **before** the token's x/y change, and on the dragging client the document still has the old position: use the **`moveToken` hook** (`movement.origin`, `movement.destination`) or the update's `change`.
- Token moves animate; reading x/y right after `move()` can show the old value; background tabs can hang the animation.
- **Tile x/y is the centre** (mesh anchor .5). Overhead tiles: RADIAL occlusion cuts a hole round each token; FADE on one big tile fades all of it.
- Level background is on `scene.levels[i].background.src`, not the scene.
- **Never create placeables right after an update that makes clients redraw (14.370, proven):** scene size or padding, grid, or a level's picture. While a client redraws, `canvas.<layer>.objects` is null, but the document's `_onCreate` still makes and draws an object, and then the layer's own draw makes a second one. The first belongs to nothing. For regions it leaves a pale white patch in `canvas.regions._highlights` that survives scene changes until reload. Do all document changes first and the redraw-causing update last (size and level together in one `scene.update`, with the full `level.toObject()`). Compute the new offsets beforehand with `scene.grid.calculateDimensions(w, h, scene.padding)`. Other clients can't be awaited, so ordering is the only reliable fix on the acting client.
- Destroying a placeable sets `document._object = null` and `document._destroyed = true`. To remove a stray copy, restore both for the live object.
- A tile with no `name` gets one from its file since 14.370: set `name` on tiles a module creates.
- PF2e difficult terrain region behaviour `modifyMovementCost` (1/2/3 per action): set `travel` as well as `walk` (PF2e tokens use travel outside combat).
- Walls: a one-way ring (`dir` LEFT, vertices in increasing angle) blocks entry and counts once for sight; LIMITED sight = see past one, not two. Test sight with `ClockwiseSweepPolygon.create(origin, {type:"sight"}).contains(x, y)` or `CONFIG.Canvas.polygonBackends.sight.testCollision(a, b, {mode:"any", type:"sight"})`. Group a ring's wall documents by position: collection order isn't creation order. Use `CONST.EDGE_SENSE_TYPES` and `CONST.EDGE_DIRECTIONS` (the `WALL_` versions go in V16); `CONST.WALL_MOVEMENT_TYPES` is not deprecated.
- Scripted moves stop at walls even for the GM, unless the update's options carry `movement: {[tokenId]: {constrainOptions: {ignoreWalls: true, ignoreCost: true}}}`. Build that options object fresh for every update: core defines a property on it, and reusing it throws "Cannot redefine property: <tokenId>". Scripted GM moves work while the game is paused (14.370). `TokenDocument#move(waypoints, options)` can't pass `constrainOptions` (they land in the update's options, unread); for waypoints that pass walls use `scene.moveTokens({ [id]: { waypoints, constrainOptions: { ignoreWalls: true } } })` (14.370).
- **Movement cost (14.370, PF2e 8.7.0):** `tokenDoc.measureMovementPath(token.createTerrainMovementPath(waypoints), {cost: CONFIG.Token.movement.TerrainData.getMovementCostFunction(tokenDoc, {})}).cost` equals what a real `TokenDocument#move` charges (`moveToken`'s `movement.passed.cost`). Difficult terrain adds 5 ft per square entered. In a fight the count of diagonals runs across the turn (PF2e rules) and Foundry charges a move as the rest of the token's `movementHistory`, which is cleared at the next turn. Foundry has no pathfinding: `Token#findMovementPath` only adds terrain waypoints and constrains at walls. Walls for a route: `CONFIG.Canvas.polygonBackends.move.testCollision(a, b, {mode: "any", type: "move"})` between token centres.
- **Foundry prices height as a plain third axis** (14.370): a move that changes elevation is charged as straight-line distance with height as one more axis, not by PF2e's flying rules, so a module that moves creatures up and down prices height itself. A height change made while crossing a square also counts as a diagonal in Foundry's own 5-10 count, so the next move can be booked 5 ft more than planned.
- **Every browser holds every journal and every scene's flags, whatever the ownership** (14.370, seen 2026-11-11 as a player): a journal with no ownership isn't in the player's sidebar and can't be opened, but `game.journal` has it with its pages and their flags, and `scene.flags` likewise. A module can't keep world data from a player who opens the console: don't put secrets in flags or GM-only journals and call them hidden.
- **A page running as the Bridge's own user can't upload a file** (`FilePicker.upload` answers false: "User [] does not have permission to upload files", 2026-11-10); the same call on a hidden AI session works.
- **Deleting the current combatant passes the turn with no `updateCombat` carrying `turn`** (14.370, PF2e 8.7.0, seen live twice 2026-11-10): the turn number stays the same, the next survivor is simply up, and core fires `combatTurnChange` and the system's turn start (`pf2e.startTurn`, `roundOfLastTurn`) only. A module that notices turn changes in `updateCombat` (`"turn" in change`) misses that turn. Also listen to `combatTurnChange` and `deleteCombatant`, and compare the combatant now up with the one last handled, a moment later so an ordinary turn change isn't handled twice (Encounter Builder's `onTurnHandedOn`, 0.24.0).
- **Read `Combat#previous` before anything awaits:** it is overwritten by the next turn change, so a value read after an `await` can already describe a later turn (14.370).
- **A Region rectangle's `x` and `y` are its top-left corner** (`anchorX`/`anchorY` default 0, 14.370), unlike a tile's centre.
- **`FilePicker.implementation.upload` into a module folder that doesn't exist yet** returned nothing usable and left the scene with no picture (14.370). Upload test pictures into a world folder (`worlds/<world>/<folder>`) after `FilePicker.implementation.createDirectory("data", path)`.
- PF2e's distance between tokens is `measureDistanceCuboid` (not exported; read it in `systems/pf2e/pf2e.mjs`): squares between edges, every second diagonal double, height as a third axis when elevations differ, and with `reach: 10` exactly, 5 ft off when there's more than one diagonal. `token.distanceTo(target, {reach})`.
- PF2e Visioner derives cover from walls: any walls a module adds affect cover; test with it.
- **A PF2e effect with a ChoiceSet (e.g. Effect: Cover) opens a prompt when added by script** (PF2e 8.7.0): set the rule's own `selection` on the source before creating it (find the rule by `key === "ChoiceSet"`); `flags.system.rulesSelections` doesn't skip it. On a page nobody watches, the prompt hangs the script.
- **What kind of creature a token is (PF2e 8.7.0, seen live 2026-11-10):** an unlinked token's own actor carries the token's name (a token renamed "Ally Goblin" had `actor.name` "Ally Goblin" and `baseActor.name` "Goblin Warrior"), and PF2e's Elite or Weak adjustment renames nothing (`actor.isElite` / `isWeak` say so). Read `token.baseActor.name` plus those two, never `actor.name`.
- **PF2e Ranged Combat consumes ammunition:** a test archer with 0 arrows fails its shots silently. Check `itemTypes.ammo` before a ranged test.
- **A module's `active` can't be redefined** on its `game.modules` entry. To test a fallback for another module being off on one page only, patch `game.modules.get` for that id (from your own module's stack) and restore it in a `finally`.
- `game.users.activeGM` may be Rhea's account when she's online: GM-side hooks then run in her browser.
- `pf2e.startTurn` fires on the active GM only. Any other client notices a turn change from `updateCombat` (`"turn" in change || "round" in change`). Don't key anything on `combat.turn` within a turn: Workbench moves a PC's initiative at 0 HP, which changes it mid-turn (PF2e 8.7.0).
- **An initiative change during a turn can hand the turn on** (PF2e 8.7.0, 14.370): PF2e's `setMultipleInitiatives` tries to keep the current creature by updating `turn` afterwards, but the page's own copy has often already shifted, so the update sends nothing and the server keeps the old turn number: the next creature becomes current, with turn events. Workbench's move of a PC at 0 HP runs in `preUpdateActor`, on whichever page applied the damage. Seen from the Bridge's page whether or not it was the active GM, and only in real monster turns, not with a bare HP change. The fix that held: in `preUpdateCombatant` set `options.combatTurn` (where the current creature will sit) and `options.turnEvents = false`, as core's `rollInitiative` does, then in `updateCombatant` save the turn with `combat.update({turn}, {diff: false, turnEvents: false})`. **Core applies `combatTurn` only in each page's copy and never saves it,** and `diff: false` is needed because the page's copy already matches. Read the server's value with `CONFIG.Combat.documentClass.database.get(...)`: a page's copy can disagree.
- **Moving a creature's initiative right after `combat.nextTurn()` can leave the turn pointer on the wrong creature** (Encounter Builder 0.12.0's Delay, 14.370, PF2e 8.7.0): the server kept the turn number `nextTurn` wrote, which after the re-sort named the moved creature again, even with `keepTurn` on the runner. Note whose turn it is after `nextTurn`, re-sort, then save `combat.update({ turn: <its new index> }, { diff: false, turnEvents: false })` yourself.
- **PF2e HUD has its own Delay:** its tracker's hourglass sets the combatant flag `pf2e-hud.delayed`; a second press re-places the creature right after the current one and calls `nextTurn` (nothing when it is already there). A module that delays creatures can set and clear that flag so the tracker shows it (`claude/foundry-s8-hud.md`).
- **Requests keyed by round and combatant break when one creature gets two turns in a round** (a Delay): mark the finished one so the turn-start guard lets the second through.
- `game.time.serverTime` is the server's clock, the same on every page, but it counts from the server's start and restarts with each world launch. Use it to compare times written by different browsers, and treat a stored time ahead of now as stale. **A stored time can also come true again by itself in a later launch** (the new clock reaches the old number: Encounter Builder's listening light turned on with nobody listening, 2026-11-10), so keep the launch beside the time: `game.world.lastPlayed` is the same text on every page of one launch and changes at each launch (seen 14.370).
- **PF2e runs a creature's turn start and turn end once a round** (the combatant's `flags.pf2e.roundOfLastTurn` and `roundOfLastTurnEnd`, PF2e 8.7.0, seen live 2026-11-10): a creature that gets a second turn in the same round (a Delay, by a module or by PF2e HUD's hourglass) fires neither `pf2e.startTurn` nor `pf2e.endTurn` again, and its persistent damage isn't applied twice. `roundOfLastTurn` naming the current round is also the sign that PF2e's turn start has reached a page.
- **Reading a creature at its turn start: wait for quiet, not a flat time.** Start-of-turn work (PF2e's turn events on the active GM's page, Workbench's Stunned and persistent damage, effects running out) reaches other pages as a burst of actor, item and combatant updates, and nothing says when it is over. Measured 2026-11-10 with every GM page on the server PC: the last change 100 to 300 ms after the turn change, gaps under 70 ms. Wait for `roundOfLastTurn` to name the round, then for about 300 ms with no change, with a floor and a cap (Encounter Builder's `settle`, `docs/features/turn-loop.md`). A relaunch also leaves the game paused: read `game.paused` before judging anything that runs by itself.
- Activating a scene pulls every client's view, including the Bridge's page. `scene.view()` resolves once the draw is finished, so wait on that and not on a `canvasReady` hook. An activation already on its way can beat your view: check again afterwards. Bridge map jobs (a sheet redraw, the exploration carry) don't move its view (14.370).
- Targets per account: `token.object.setTarget(true, {user: game.user, releaseOthers: true, groupSelection: false})` to set, `canvas.tokens.setTargets([], {mode: "replace"})` to clear; `game.user.updateTokenTargets` is gone. Other clients see the mark through `targetToken` (14.370).
- The browser tool's `left_click_drag` is unreliable on the canvas: it moved a token once at zoom 1 (2026-11-02) but failed to move notes and tokens in later sessions. Always check the result; the reliable ways are `TokenDocument#move` (what a drag calls) or pointer events on `canvas.app.view` (snippet in `claude/lythara-survey-sheet-module.md`).
- One login cookie per browser: logging Test Player in makes uploads from the AI tab fail until AI rejoins.
- Embedded collections (`scene.tokens`, `scene.walls`) have `map` and `filter` but not `flatMap`: use `.contents`. Local tests with plain arrays won't catch it.
- A journal page at exact LIMITED can't be opened from a map note unless it's an image (`Note#_canView`, 14.370): use OBSERVER. A player without LIMITED on the journal itself can't open its sheet either, so open such a page yourself from an `activateNote` hook that returns false.
- PF2e loot actors get LIMITED for all whatever you create them with, which is enough for a player to open a revealed one.
- **Two turn changes within about 200 ms: `combat.combatant` can read the creature before for a moment** (14.370, PF2e 8.7.0, seen 2026-11-11 on a GM page that wasn't the active GM: work queued at the second change read the first change's creature about 100 ms after the second had arrived, then the right one again). A module that decides whose turn it is once, straight after `updateCombat`, can decide for the wrong creature and never look again (Encounter Builder missed a ticked monster's turn in three of four tries when its own Auto turn end and a next-turn call came 200 ms apart). Look again about a second later, and make that look safe to repeat.
- **Taking one user's entry out of a document's `ownership`** (14.370, 2026-11-11): `update({"ownership.-=<userId>": null})` and a `ForcedDeletion` value both left the entry in place on an actor; replacing the whole object did it: `update({"==ownership": {...without that user}})`. Check `Object.keys(doc.ownership)` afterwards.
- **The browser pane draws no canvas while it isn't shown** (2026-11-11): joined to the game with the pane hidden, `game.ready` was true and `canvas.ready` stayed false for as long as it was looked at, so a script waiting for the canvas never returns and no picture of a player's map can be had from there. A hidden test session computes no sight either (a token in plain view reads `isVisible` false). A picture of a player's map needs the pane on screen: ask Rhea to show it first.
- **Deleting the current combatant moves the turn on by itself** (core's `Combatant._preDeleteOperation` hands it to the next survivor with turn events, 14.370). Calling `combat.nextTurn()` first and then deleting skipped the next creature's turn (round 1 → 2). Just delete.
- **`combat.rollInitiative(ids)` opens PF2e's roll dialog on the calling page** when that user's check dialogs are on (fresh hidden sessions and the pane both default to on), and waits for ever where nobody clicks. Pass `{ skipDialog: true }`; it goes through to the statistic roll. `combat.rollAll()` has the same trap.
- **A hidden token is still a creature to your own code** unless you filter it: the Encounter Builder's route check and its ally list both counted an escaped (hidden) token until 0.11.0. Decide per use whether `hidden` tokens take part.
- A timeout on another module's long job (a Survey Sheet redraw) doesn't stop the job; never offer the button that started it again on a timeout.
- `applyAdjustment("weak"|"elite")` on a world actor, `getTokenDocument({x, y})`, `actor.inventory.addCoins({gp, sp, cp})` and `increaseCondition("unconscious")` on a token's own actor all work for unlinked tokens (PF2e 8.7.0).
- **What a module sees of a player's action (14.370, PF2e 8.7.0, seen live 2026-11-09):** a real token drag is one `moveToken` with `movement.method` "dragging" and one passed waypoint a square, each with its movement action (a scripted move is "api"); Foundry has no Step movement action, so a one-square walk can't be told from a Step. Cards from `game.pf2e.actions.get(x).use()` (Interact, Stand, Step, Drop Prone) have an empty `flags.pf2e`: the title (`<h4 class="action"><strong>`) and trait tags (`class="tag" data-slug`) are only in the flavor HTML. Drawing or stowing through `actor.changeCarryType` posts no card (only `updateItem` on `system.equipped`). A spell's cast card has `flags.pf2e.casting` and its traits in `origin.rollOptions`; its attack roll's options hold `item:ranged` and `item:type:spell`. A consumable's `flags.pf2e.origin` is on its card whether it was used or only shown in chat (an `item-card` in the content), and one used up no longer resolves by uuid (its `sourceId` does). PF2e rolls a melee Strike at a target that has moved out of reach.
- **What PF2e's cards record of damage and healing (PF2e 8.7.0, Toolbelt 3.60.0, probed live 2026-11-11):** the **damage-taken** card (`flags.pf2e.context.type === "damage-taken"`, posted by whoever pressed Apply, its speaker the creature that took it) carries `flags.pf2e.origin` (the attacker's actor uuid and item uuid, when applied from a card) and `flags.pf2e.appliedDamage`: `isHealing`, `shield`, `persistent` (ids of conditions it started) and `updates`, which holds **what was taken off** HP and temporary HP for a revert (23 for a hit that left 57 of 80), not the HP before. A weakness, resistance or immunity applied is **only in the card's HTML** (`data-applications` on the `.iwr` span, GM-visible). The HP update arrives **before** the card; a hit brought to nothing (resisted, immune, a shield taking all of it) has a card with `appliedDamage: null` and **no** HP update. Persistent damage at the end of a turn is rolled and applied on the active GM's page with origin type `condition`. A condition item names no source (`origin` is its bearer). Toolbelt rolls a save from its row with **no chat card**: the result is a flag update on the damage card (`flags.pf2e-toolbelt.targetHelper.saveVariants.null.saves[tokenId].success`).
- **An HP update's `damageTaken` option isn't always there** (PF2e 8.7.0, 2026-11-11): a card's damage carries it, and so does a hand edit of a linked actor, but a hand edit of an **unlinked token's** actor carries none. A watcher that needs "how much" keeps the HP it last saw. `preUpdateActor` fires only on the page that made the change: watch `updateActor` from any other page.
- **A redraw that waits while a text box has focus must wait for the whole panel around it:** focus leaves the box when the mouse goes down on the button beside it, and a redraw between the press and the release replaces the button, so the click is lost (found by a review, 2026-11-11). Test the container, and release the wait when focus leaves the container.
- **A job another module runs on a page dies with that page** (2026-11-11: a map extension on the runner's page, the page reloaded, the map never grew, and the card said it had): after a reload, check what the job actually did (keep the size from before and compare) before treating it as done.
- **A resistance to "all-damage" applies to each damage type of a roll, and two of them count as the higher only** (PF2e 8.7.0, seen live 2026-11-11: 8 slashing and 6 fire against resistance 5 took 4 off HP; two effects of 5 and 2 gave 5). A flat reduction is not a resistance: take it off the roll with `roll.alter(multiplier, -n)`, which keeps the damage types and takes it off the first instance (`8 - 2 slashing + 6 fire`). **A resistance for one application only** needs nothing on the real creature: `actor.getContextualClone(rollOptions, [effectSource])` takes effect sources, and `clone.applyDamage(...)` works the damage out on the copy, updates the real HP and shows the resistance on PF2e's damage-taken card (which is public; only its IWR details are GM-only).
- **A damage formula with two types needs braces:** `new DamageRoll("{8[slashing],6[fire]}")` has two instances; `8[slashing]+6[fire]` evaluates as one untyped instance, so a probe built on it proves nothing about types (2026-11-11).
- **`actor.applyDamage` needs a token** (PF2e 8.7.0): for a world actor with no token it throws inside PF2e ("Cannot read properties of null (reading 'name')"). A token document on a scene nobody is viewing is enough.
- **PF2e writes an effect's `system.start` itself when the effect is made** (8.7.0: a start passed in the source came back with `initiative: null` outside a fight): to count an effect's rounds from a creature's own initiative, update `system.start` just after creating it. With `duration.expiry: "turn-end"` an effect of 1 round started at a creature's initiative on its own turn ends at the end of its next turn. `automation.removeExpiredEffects` decides whether it is then deleted.
- **`TokenAura#containsToken` answers false on a scene that isn't drawn on the page** (two tokens side by side, 2026-11-11): use it only when both tokens have a canvas object. The aura's radius is on `token.auras.get(slug)` and `actor.auras.get(slug)`; a champion's aura exists only while its toggle is on and its bearer is conscious.
- **PF2e tracks no reaction use** (8.7.0, 2026-11-11: nothing on the actor's resources or attributes; no installed module had a setting for it): a module that needs "has it reacted this round" keeps that itself. PF2e HUD marks a Delaying creature with the combatant flag `pf2e-hud.delayed`.
- **Workbench's Learn a Spell stops a spell being added to a character by script** (xdy-pf2e-workbench 7.7.5, world setting `enableGeneralLearnSpell`, seen 2026-11-11): its `preCreateItem` hook returns false for a spell created on a character and opens its own dialog on the creating page (six were left open on the Bridge's page, each named after the spell); `createEmbeddedDocuments` answers an empty list with no error, and no later `preCreateItem` hook runs. An NPC is not affected. For a test character in PF2 Test: turn the setting off, create the spell, turn it back on, and close any dialog it left. Seen again 2026-11-11 evening: with that dialog still open on the page, a second create of the same spell (`Item.implementation.create(data, {parent: actor})`) went through; why wasn't looked into, so don't rely on it, and read the page's dialogs afterwards either way.
- **Rigging a d20 with `CONFIG.Dice.randomUniform`: high numbers roll low** (Foundry 14.370, seen 2026-11-11): `() => 0.2` rolled 16, `() => 0.08` rolled a critical success and `() => 0.92` rolled 2. It rigs every die on that page (damage too), so set it only around the roll, keep the original in a variable on `window` when the roll happens in another call, and put it back in a `finally`.
- **A damage-taken card arrives after the hit points are written** (PF2e 8.7.0, seen live 2026-11-11 through Toolbelt's Target Helper row and a real click on Damage): when another page's `createChatMessage` hook reads the card, the creature it speaks for is already at its new hit points, so a blow that drops it shows 0 there and the creature already counts as down. Anything that asks "was it awake when this landed" answers no for the killing blow: keep what you need about that blow from the card itself (its `flags.pf2e.origin`), not from the creature's state.
- **A creature dropped to 0 moves in the initiative order, so a test must never step turns by count** (PF2e 8.7.0, 2026-11-11): a character taken to 0 hit points is put just before the creature that dropped it, and the note on the card says so. A test driver that called `nextRound()` and then `nextTurn()` once landed on the wrong creature. Step until `combat.combatant.tokenId` is the one wanted, and wait about 2 s after each step when a module makes a request at a turn's start (stepping faster left two requests for one turn in Encounter Builder).
- **A creature's side and owners, and what fires when they change (PF2e 8.7.0, 14.370, probed live 2026-11-13).** `actor.alliance` is `system.details.alliance` when that is set ("party", "opposition", or `null` for nobody's side); when it is unset it is "party" for an actor a player owns and "opposition" otherwise, so **giving a player ownership of an NPC changes its side too**, with no alliance update at all. Setting the side on an unlinked token's actor (`token.actor.update`) fires `updateActor` for the synthetic actor (`actor.isToken` true, the change holding `system.details.alliance`) and `updateActorDelta`, and **not `updateToken`**. Ownership lives on the world actor: giving it fires `updateActor` on that actor with `ownership.<userId>`, taking it away (the `==ownership` replace) with `ownership`; a token's synthetic actor reads `hasPlayerOwner` from it at once and fires nothing of its own. A module that keeps anything per side should compare with what it stored at each turn change as well, since a hook can be missed while its page reloads.
- **A character's gender is free text, and an NPC has none (PF2e 8.7.0, read live 2026-11-13).** A character sheet's Gender box is `actor.system.details.gender.value`, a plain string the player types ("", "Female", "he/him", "non-binary"): read it by its first telling word and treat empty as unknown. NPC actors have no such field, so a monster's pronoun has to live in the module's own data. Text that must read right for "they" needs every verb the pronoun governs in both forms, not only the first ("they have yielded and stand down").
- **PF2e makes no combatant for a creature with the minion trait** (8.7.0, 2026-11-11: `combat.createEmbeddedDocuments("Combatant", ...)` for a minion's token answered nothing, with no error): a minion acts on its master's turn and is never in `combat.combatants`. **`game.pf2e.actions.get("raise-a-shield")` is undefined** in 8.7.0; `game.pf2e.actions.raiseAShield({ actors: [actor] })` works. **An aura's `containsToken` is false for a creature behind a wall or trunk** even when it is within the radius (15 ft away, a trunk between: false; another creature at 15 ft in the open: true): PF2e tests line of effect, so don't replace it with a distance test where the map is drawn.

- **Core's own sidebar buttons use `data-action` too** (14.370, seen 2026-11-13): `button[data-action="export"]` matched a sidebar button (the floppy-disk export) before a module window's Export, and a real click on the first match pressed core's. Scope a test's selector to the window (`#<app id> button[data-action="export"]`), and in the module's own code look buttons up inside its own element.
- **PF2e reports a creature's adjusted level for Elite and Weak, with the +2 / -2 edges** (PF2e 8.7.0, probed live 2026-11-13 on Monster Core creatures): `actor.level` after `applyAdjustment("elite")` is the base +1, or +2 at base -1 or 0; after `"weak"` the base -1, or -2 at base 1 (Elite -1 → 1, Elite 0 → 2, Weak 1 → -1, Weak 2 → 1). The unadjusted level stays in `actor._source.system.details.level.value`, and the adjustment in `system.attributes.adjustment`. The adjusted level can't be turned back for certain (Elite 0 and Elite 1 both read 2): read the source's level for the base creature.

## 9. Canvas and performance lessons
- Chrome defers canvas drawing; per-stage timings land at the next flush. Time a stage with `ctx.getImageData(0,0,1,1)` after it.
- `filter: blur()` on a big canvas costs a whole-canvas pass per call: blur on a small scratch canvas and composite (38 s → 0.5 s).
- Batch many small shapes into one `Path2D` per colour; interleave passes if draw order matters.
- Precompute fields (slope, distance) instead of sampling noise repeatedly per pixel; cache per-map seed points.
- Avoid per-pixel random noise for texture (reads as TV static); build texture from shapes. Know your noise table's feature size (Lythara's `tbl`: ~23 units per feature, so `tbl(x * 23 / F)` gives F-unit features).
- Always look at a whole output scaled down and a close crop.
